# План реализации Personal Assistant

## Текущий статус

- Phase 1: код и нативные проверки завершены; container smoke test ожидает восстановления Docker Desktop.
- Phase 2: базовый Telegram-бот запущен через polling, health endpoint и Telegram update проверены на локальной SQLite fallback-базе.
- Phase 3: реализованы structured extraction, forward и voice pipeline; live-транскрипция ожидает `OPENAI_API_KEY`.
- Phase 4: реализованы Telegram initData auth, REST CRUD/settings и mobile-first Kanban; браузерный smoke test и открытие через Telegram пройдены.
- Phase 5: реализованы реальные RSS/Atom-источники, нормализация, дедупликация, локальный/LLM ranking, structured summaries, JSON preview и идемпотентное сохранение DailyDigest.
- Phase 6: реализована генерация и выдача PDF; шаблон WeasyPrint используется в Docker, а локальный Windows fallback не требует GTK.
- Phase 7: реализованы APScheduler, идемпотентная утренняя доставка задач/PDF, `/news` и очистка временных PDF; live-доставка проверена в Telegram.
- Phase 8: реализованы API архива, HTML-view сводки и скачивание PDF в Mini App; мобильный браузерный smoke test пройден на реальных данных.
- Phase 9: реализованы защищённый webhook, сетевые retries, production nginx/Compose и полная инструкция VPS; container build заблокирован сломанным runtime Docker Desktop на текущем ПК, нативный production-like smoke test пройден.

## Цель MVP

Собрать однопользовательский Telegram-бот и Telegram Mini App для быстрого сохранения задач, утреннего списка дел и ежедневной PDF-сводки реальных новостей со ссылками на источники.

## Архитектурные решения

- Monorepo: `backend`, `frontend`, `nginx` и общая Docker Compose-конфигурация.
- Один Python-проект объединяет FastAPI, aiogram и APScheduler, но их код разделён по пакетам.
- PostgreSQL — единственное постоянное хранилище; Redis, Celery и отдельные микросервисы не используются.
- SQLAlchemy 2 работает асинхронно через `asyncpg`; миграции выполняет Alembic.
- REST API доступен под `/api`; Mini App передаёт Telegram `initData`, которое проверяется на backend.
- В production nginx раздаёт собранный React frontend и проксирует `/api` к backend.
- Bot polling используется локально, webhook поддерживается production-конфигурацией.
- News pipeline получает статьи только через провайдеры RSS/Atom или API. LLM не создаёт факты, а только извлекает, ранжирует и суммирует данные в структурированном формате.
- PDF создаётся из Jinja2-шаблона через WeasyPrint и сохраняется в постоянный volume.
- Утренняя задача идемпотентна: одна основная `DailyDigest` на календарную дату и статусы `pending/processing/completed/failed`.

## Модель данных

- `tasks`: задача, исходный Telegram-контент, статус, важность, дедлайн и временные метки.
- `news_articles`: нормализованные статьи и оценка релевантности.
- `daily_digests`: дата, путь к PDF, статус и ошибка генерации.
- `digest_articles`: связь сводки со статьями, порядок, раздел и короткие тексты.
- `user_settings`: настройки единственного владельца, темы, время, часовой пояс и число новостей.

## Этапы

### Phase 1 — основа

- Создать структуру monorepo и конфигурацию окружения.
- Добавить PostgreSQL, backend, frontend/nginx в Docker Compose.
- Реализовать настройки приложения, async database session, модели и первую Alembic-миграцию.
- Реализовать FastAPI и `GET /api/health` с проверкой базы.
- Проверить сборку контейнеров, миграцию, healthcheck и синтаксис Python/JSON/YAML.

Критерий готовности: `docker compose up --build` поднимает PostgreSQL, применяет миграцию, запускает backend и отдаёт успешный `/api/health` напрямую; production-конфигурация дополнительно отдаёт его через nginx.

### Phase 2 — базовый Telegram-бот и задачи

- Добавить owner-only middleware и команды `/start`, `/tasks`, `/today`, `/app`, `/help`.
- Создавать текстовые задачи без потери исходного сообщения.
- Добавить inline-действия: завершить и удалить.
- Реализовать task repository/service и необходимые REST-схемы.
- Покрыть создание, изменение и завершение задач тестами.

Критерий готовности: владелец создаёт, видит, завершает и удаляет задачу через Telegram; прочие пользователи не получают доступ.

### Phase 3 — извлечение данных, forward и voice

- Реализовать `LLMService` со структурированными Pydantic-ответами.
- Извлекать только явно указанные название, дедлайн и важность с текущими датой и часовым поясом.
- Добавить forwarded messages и сохранение доступных сведений об источнике.
- Добавить скачивание `.ogg`, транскрипцию и отмену только что созданной voice-задачи.
- При сбое OpenAI сохранять текстовую задачу как есть.

Критерий готовности: текст, forward и voice создают задачи; поддерживаемые относительные даты переводятся в абсолютное время; сбой LLM не теряет текст.

### Phase 4 — Telegram Mini App

- Проверять подпись Telegram WebApp `initData` и owner ID; оставить явный dev-режим.
- Реализовать REST CRUD, move и complete.
- Собрать mobile-first React-интерфейс с Kanban, drag-and-drop, формой и bottom sheet.
- Добавить вкладки «Задачи», «Сводки», «Настройки» и TanStack Query.

Критерий готовности: авторизованный владелец управляет задачами в Mini App; поддельный или чужой `initData` отклоняется.

### Phase 5 — news pipeline

- Создать общий интерфейс `NewsProvider` и конфигурацию расширяемых RSS/Atom/API-источников.
- Получать публикации за 24 часа, нормализовать и сохранять их.
- Удалять дубли по URL, нормализованному заголовку и безопасной fuzzy-схожести.
- Ранжировать и суммировать статьи через structured output OpenAI.
- Сначала сохранять и проверять результат сводки как JSON.

Критерий готовности: pipeline возвращает 8–15 или меньше действительно значимых реальных статей с исходными URL; при пустой категории явно фиксирует отсутствие важных новостей.

### Phase 6 — PDF

- Создать минималистичный A4-шаблон Jinja2/CSS с разделами, датой, страницами и кликабельными ссылками.
- Генерировать `daily_digest_YYYY-MM-DD.pdf` через WeasyPrint.
- Визуально проверить рендер нескольких страниц и кириллицу.

Критерий готовности: PDF открывается, читается, содержит выбранные новости и рабочие ссылки на первичные публикации/СМИ.

### Phase 7 — scheduler и доставка

- Настроить APScheduler по `DAILY_DIGEST_TIME` и `TIMEZONE`.
- Реализовать идемпотентный `daily_digest_job` и безопасный `cleanup_job`.
- Независимо отправлять утренние задачи, статус сводки и PDF.
- Добавить retries внешних запросов и структурированные логи без секретов.

Критерий готовности: тестовый запуск job создаёт не более одной сводки на дату и отправляет сообщение/PDF; ошибка новостей не мешает отправке задач.

### Phase 8 — архив сводок

- Реализовать API списка, HTML-представления и PDF сводок.
- Подключить вкладку «Сводки» в Mini App.
- Не регенерировать сегодняшнюю завершённую сводку по `/news` без явной необходимости.

Критерий готовности: прошлые сводки открываются в Mini App и скачиваются как PDF.

### Phase 9 — production hardening

- Добавить webhook-конфигурацию, production nginx/TLS-инструкции и ограничения доступа.
- Проверить обработку ошибок, таймауты, retries, логирование и сохранность volume.
- Дописать пошаговый README: BotFather, user ID, Mini App, env, миграции, polling/webhook и VPS.
- Выполнить полный прогон тестов, lint/typecheck, Docker build и smoke test.

Критерий готовности: все семь пользовательских сценариев проходят на production-подобном окружении.

## Границы MVP

Не добавлять проекты, теги, повторяющиеся задачи, календарь, чат с LLM, аналитику, роли, совместную работу и другие интеграции. Новые абстракции вводить только там, где они нужны текущему сценарию или уже явно предусмотренному провайдерному интерфейсу.

## Общая стратегия проверки

- После каждого этапа: запуск приложения, целевые тесты, полный тестовый набор, lint/typecheck и smoke test.
- Python: `python3 -m compileall` и pytest.
- JSON/YAML: отдельная синтаксическая проверка.
- Frontend: TypeScript build и lint.
- Docker: build, healthchecks, применение миграций и запрос к `/api/health`.
- Важные этапы: независимая проверка reviewer-субагентом перед фиксацией результата.
